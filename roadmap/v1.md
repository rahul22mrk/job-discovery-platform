# V1 Roadmap

## 1. Roadmap Goal

The goal of V1 is to build and validate the core job discovery engine.

V1 is not a complete job portal.

The first version should prove that the platform can:

- Accept a user's search
- Discover relevant public pages
- Identify walk-in opportunities
- Extract useful information
- Normalize the data
- Validate the opportunity
- Remove duplicates
- Track freshness
- Store the result
- Return useful opportunities to the user

The roadmap is intentionally incremental.

We should build the smallest useful system first and add complexity only when it is justified.

---

# 2. V1 End Goal

A user should eventually be able to do:

    Search:
    Bengaluru + Java + 3-5 years

and get:

    Upcoming Walk-in Opportunities

with information such as:

- Company
- Role
- Location
- Interview date
- Interview time
- Venue
- Experience
- Skills
- Source
- Last checked
- Status

The user should be able to open the original source page.

- Configure application profiles
- Configure Git
- Configure basic logging
- Create initial package/module structure
- Create basic health endpoint
- Add README for backend setup

## Expected Structure

    backend/
    ├── src/
    │   ├── main/
    │   │   └── java/
    │   └── test/
    ├── pom.xml
    └── README.md

Logical modules can initially be:

    discovery
    extraction
    normalization
    validation
    deduplication
    ranking

The backend should:

- Start successfully
- Connect to PostgreSQL
- Run tests
- Expose a health endpoint

# 5. Phase 1 — Discovery Contract

## Goal

Define the internal contracts for discovery.

The discovery layer should not depend directly on one provider.

## Tasks

Create concepts for:

- SearchContext
- DiscoveryTask
- DiscoveredPage
- JobSource
- QueryGenerator

Example interface:

    public interface JobSource {

        List<DiscoveredPage> discover(SearchContext context);

    }

## Search Context

The search context should contain information such as:

- City
- Keyword
- Experience
- Date range
- Opportunity type

## Completion Criteria

The system should be able to accept:

    Bengaluru + Java

and convert it into a structured search context.

---

# 6. Phase 2 — Query Generation

## Goal

Convert user search criteria into useful discovery queries.

Example:

    Bengaluru + Java

can produce:

    "walk-in interview" "Bengaluru" "Java"
    "walk-in drive" "Bengaluru" "Java"
    "walkin interview" "Bengaluru" "Java"
    "walk-in recruitment" "Bengaluru" "Java"
    "Java developer" "walk-in" "Bengaluru"
    "Java backend" "walk-in" "Bengaluru"

## Tasks

- Implement QueryGenerator
- Add walk-in keywords
- Add technology aliases
- Add role aliases
- Add city normalization
- Avoid unnecessary duplicate queries

## Completion Criteria

Given the same search criteria, the system should consistently generate useful query variations.

---

# 7. Phase 3 — Search Provider Integration

## Goal

Discover candidate URLs from a search provider.

The initial implementation should use one provider.

The provider should be hidden behind an internal interface.

Example:

    SearchProvider
         ↓
    SearchProviderSource

The business logic should not depend directly on provider-specific response objects.

## Tasks

- Select initial provider
- Configure credentials securely
- Implement provider adapter
- Execute generated queries
- Extract result URLs
- Store basic source information
- Handle provider errors
- Handle rate limits

## Completion Criteria

Input:

    Bengaluru + Java

Output:

    List of candidate URLs

Example:

    URL 1
    URL 2
    URL 3
    URL 4

No job extraction is required yet.

---

# 8. Phase 4 — URL Processing

## Goal

Clean and deduplicate discovered URLs before fetching them.

## Tasks

- Normalize URLs
- Remove obvious tracking parameters where safe
- Detect duplicate URLs
- Store source information
- Avoid processing the same URL multiple times

## Completion Criteria

If multiple queries return the same URL, the system should process it once.

---

# 9. Phase 5 — Page Fetching

## Goal

Fetch publicly accessible source pages.

## Tasks

Create a page-fetching component.

Responsibilities:

- HTTP requests
- Timeouts
- Redirect handling
- HTTP error handling
- Response validation
- Basic retry/backoff
- Fetch timestamp
- Failure logging

The fetcher should not know anything about job extraction.

## Important Rule

Only appropriately accessible public pages should be fetched.

The system must not bypass:

- CAPTCHA
- Authentication
- Access controls
- Other restrictions intended to prevent automated access

## Completion Criteria

Input:

    URL

Output:

    Raw page/document

or:

    Fetch failure

A failed URL must not stop the complete discovery task.

---

# 10. Phase 6 — Raw Document Storage

## Goal

Keep the original fetched information available for processing and debugging.

## Tasks

Store information such as:

- Source URL
- Source name
- Raw HTML or extracted raw content
- Content hash
- Discovered time
- Fetched time
- HTTP status
- Fetch status

Raw data should remain separate from normalized job data.

## Why

If extraction logic improves later, previously collected data may be useful for reprocessing.

It also helps investigate extraction errors.

---

# 11. Phase 7 — Generic Text Extraction

## Goal

Convert HTML into useful page text.

## Tasks

- Remove scripts
- Remove styles
- Remove irrelevant page elements
- Extract visible text
- Normalize whitespace
- Preserve useful structure where possible

The result should be a clean document suitable for further processing.

Pipeline:

    HTML
      ↓
    HTML Cleaner
      ↓
    Clean Text

---

# 12. Phase 8 — Structured Data Extraction

## Goal

Use structured information when the source provides it.

The system should inspect:

- JSON-LD
- JobPosting structured data
- OpenGraph metadata
- Other useful metadata

Google documents JobPosting structured data for job pages.

Source:

https://developers.google.com/search/docs/appearance/structured-data/job-posting

## Strategy

Prefer structured data when available.

However, structured data must still be validated against the actual page.

---

# 13. Phase 9 — Walk-in Detection

## Goal

Determine whether the page actually represents a walk-in opportunity.

## Strong Signals

- Walk-in interview
- Walk-in drive
- Walk-in recruitment
- Walk-in hiring
- Walkin
- Interview date
- Interview time
- Interview venue
- Recruitment drive

## Tasks

- Implement initial rule-based detector
- Calculate detection confidence
- Identify supporting signals
- Reject obvious non-walk-in pages

## Important Rule

The presence of the word "walk-in" alone should not automatically make a page a walk-in opportunity.

The detector should look for meaningful event evidence.

## Completion Criteria

The system should classify pages as:

    WALK_IN
    NOT_WALK_IN
    UNCERTAIN

Only sufficiently strong candidates should continue to normal opportunity extraction.

---

# 14. Phase 10 — Job Information Extraction

## Goal

Convert a walk-in page into a structured opportunity.

Initial fields:

- Company
- Job title
- Description
- City
- Country
- Opportunity type
- Event date
- Event start time
- Event end time
- Venue
- Experience minimum
- Experience maximum
- Skills
- Application information
- Source name
- Source URL

## Extraction Strategy

Use:

    Structured Data
          ↓
    Known Source Parser
          ↓
    HTML / DOM Extraction
          ↓
    Text Patterns
          ↓
    AI-assisted Extraction
          ↓
    Validation

AI should not be required for every page in V1.

## Completion Criteria

A valid candidate page should produce a structured job object.

---

# 15. Phase 11 — Data Normalization

## Goal

Convert different representations into consistent internal data.

Examples:

    Bangalore → Bengaluru

    3-5 years → min=3, max=5

    3+ years → min=3

Technology aliases:

    Java
    Java Developer
    Core Java
    Java Backend
    Java Engineer

should be mapped appropriately for matching.

## Important Rule

Normalization should not destroy the original source information.

Store normalized values separately where required.

---

# 16. Phase 12 — Validation

## Goal

Reject incorrect or low-quality opportunities before they reach users.

## Validation Rules

Check:

- Company exists
- Job title exists
- Source URL exists
- Walk-in evidence exists
- City is relevant
- Event date is valid when available
- Opportunity is not already expired
- Extracted information is not obviously corrupted

## Completion Criteria

Invalid opportunities should be rejected or marked appropriately.

The system should not silently invent missing values.

---

# 17. Phase 13 — Opportunity Deduplication

## Goal

Represent the same real-world opportunity only once.

Potential matching fields:

- Company
- Job title
- City
- Event date
- Venue
- Application URL
- Description similarity

## Initial Approach

Start with deterministic matching.

Example:

    Company
    +
    Normalized Job Title
    +
    City
    +
    Event Date

can form a strong duplicate signal.

## Future

Semantic similarity can be introduced later for difficult cases.

## Completion Criteria

The same opportunity discovered from multiple sources should be merged or linked rather than displayed as separate jobs.

---

# 18. Phase 14 — Source Management

## Goal

Track where every opportunity came from.

Source information should include:

- Source name
- Source type
- Source URL
- Source quality
- First discovered
- Last checked

Possible source types:

    SEARCH_PROVIDER
    COMPANY
    ATS
    JOB_BOARD
    AGGREGATOR
    API
    RSS
    WEB_PAGE

## Completion Criteria

Every stored opportunity must have traceable source information.

---

# 19. Phase 15 — Freshness

## Goal

Keep walk-in opportunities current.

Track:

- discoveredAt
- firstSeenAt
- lastCheckedAt
- eventDate
- status

Initial states:

    ACTIVE
    AGING
    EXPIRED

## Rules

If:

    eventDate < current date

then:

    status = EXPIRED

The system should not show expired opportunities as upcoming.

## Future

Add:

    CANCELLED
    RESCHEDULED

when change detection is implemented.

---

# 20. Phase 16 — PostgreSQL Persistence

## Goal

Persist normalized opportunities and discovery information.

Initial tables:

    companies
    job_postings
    job_sources
    job_raw_documents
    job_discovery_tasks
    job_skills
    job_posting_skills

## Important Design

The database should distinguish:

    Source
       ↓
    Opportunity

One opportunity may have multiple sources.

Example:

    Job Posting
       ├── Source A
       ├── Source B
       └── Source C

# 21. Phase 17 — Discovery Task

## Goal

Make discovery asynchronous and track its progress.

Task lifecycle:

    CREATED
       ↓
    PROCESSING
       ↓
    COMPLETED

Failure:

    FAILED

Track:

- Search criteria
- Start time
- End time
- URLs discovered
- Pages fetched
- Walk-ins detected
- Opportunities extracted
- Opportunities rejected
- Duplicates
- Errors

---

# 22. Phase 18 — Asynchronous Processing

## Goal

Prevent the user from waiting for the complete discovery pipeline.

Flow:

    User
      ↓
    Discovery API
      ↓
    Create Task
      ↓
    Async Worker
      ↓
    Discovery Pipeline
      ↓
    Database

For V1, use a simple Spring asynchronous mechanism and a controlled thread pool.

Kafka is not required initially.

Introduce a message broker only when real workload requires it.

---

# 23. Phase 19 — Search API

## Goal

Provide a simple API for users and the future frontend.

Endpoint:

    POST /api/v1/discovery/search

Request:

    {
      "city": "Bengaluru",
      "keyword": "Java",
      "experienceMin": 3,
      "experienceMax": 5,
      "fromDate": "2026-09-01",
      "toDate": "2026-09-30",
      "type": "WALK_IN"
    }

Response:

    {
      "searchId": "abc123",
      "status": "PROCESSING"
    }

A future endpoint can provide:

    GET /api/v1/discovery/search/{searchId}

for task status and results.

# 30. V1 Launch Criteria

V1 should not be considered complete simply because the code runs.

It should meet the following product criteria:

### Discovery

The system can discover relevant public walk-in pages.

### Extraction

The system can extract useful structured information.

### Relevance

A reasonable percentage of results actually match the user's search.

### Freshness

Expired events are removed from active results.

### Deduplication

The same opportunity does not repeatedly appear as separate listings.

### Transparency

Every result has a source.

### Reliability

One failed source/page does not stop the complete search.

### Usability

A user can perform a search without understanding the internal system.

---

# 31. V1 Metrics

Track these metrics during validation:

## Discovery Success Rate

Percentage of searches that produce at least one relevant opportunity.

## Relevant Result Rate

Percentage of returned results that actually match the search intent.

## Extraction Completeness

Percentage of opportunities containing key fields.

## Duplicate Rate

Percentage of results that are duplicates.

## Expired Result Rate

Percentage of results that were already expired.

## Source Success Rate

Percentage of discovered URLs that can be successfully processed.

## Fetch Failure Rate

Percentage of pages that cannot be fetched.

## Average Discovery Time

Time from search submission to results being available.

These metrics should guide future improvements.

# 37. Definition of Done

A feature is not considered done only because its code compiles.

A feature is done when:

- Implementation is complete
- Unit tests exist where appropriate
- Integration behavior is tested where required
- Failure cases are considered
- Logs are useful
- The feature works with real data where applicable
- The feature does not unnecessarily couple unrelated modules
- Documentation is updated when the behavior changes

# 40. Final Goal

At the end of V1, the platform should prove one important thing:

> A user can enter a simple job-search intent and the system can automatically discover useful upcoming walk-in opportunities from the public web, clean the information, remove duplicates, keep the data fresh, and show the original source.

If this works reliably, we have the foundation for the larger Job Discovery Platform.

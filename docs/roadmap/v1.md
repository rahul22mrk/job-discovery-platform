# V1 Roadmap

## 1. Roadmap Goal

The goal of V1 is to build and validate the core job discovery engine.

The first version focuses on automatically discovering relevant upcoming walk-in opportunities from the public web.

The main development priority is the backend.

The frontend folder will exist in the repository from Day 1, but frontend development will start after the core backend discovery pipeline and APIs are working reliably.

V1 should prove that the platform can:

- Accept a user's search
- Generate useful discovery queries
- Discover relevant public pages
- Fetch accessible pages
- Identify walk-in opportunities
- Extract useful information
- Normalize the data
- Validate the opportunity
- Remove duplicates
- Track freshness
- Store the result
- Search and rank opportunities
- Expose the results through APIs

---

# 2. Repository Structure

The project uses one GitHub repository.

    job-discovery-platform/
    ├── README.md
    ├── docs/
    │   ├── product/
    │   ├── requirements/
    │   └── architecture/
    ├── research/
    ├── roadmap/
    ├── backend/
    ├── frontend/
    ├── infrastructure/
    └── .github/

Both frontend and backend are part of the product.

However, V1 development follows a backend-first approach.

    backend/
        ↓
    discovery engine
        ↓
    real data
        ↓
    APIs
        ↓
    frontend

The frontend is not being removed from V1.

It is simply implemented after the backend has enough functionality to support a real user experience.

# 3. Development Strategy

The product should be developed in this order:

    Product Requirement
          ↓
    Backend Capability
          ↓
    Real Data Testing
          ↓
    Data Quality Improvement
          ↓
    API
          ↓

The most important technical risk in V1 is automatic discovery from the public web.

Therefore backend discovery is the first priority.

# 5. Phase 1 — Domain and API Contracts

## Goal

Define the internal domain model before implementing the complete discovery pipeline.

## Tasks

Create concepts for:

- JobPosting
- Company
- JobSource
- RawDocument
- DiscoveryTask
- SearchContext
- JobOpportunityType

Example opportunity types:

    WALK_IN
    JOB
    HIRING_DRIVE

V1 primarily uses:

    WALK_IN

## Search Context

SearchContext should support:

- City
- Company
- Keyword
- Skills
- Opportunity type
- Minimum experience
- Maximum experience
- From date
- To date

## Completion Criteria

The backend has clear domain models and interfaces that do not depend on external providers.

---

# 6. Phase 2 — Query Generation

## Goal

Convert a user's search intent into useful web discovery queries.

Example:

    Bengaluru + Java

can produce:

    "walk-in interview" "Bengaluru" "Java"
    "walk-in drive" "Bengaluru" "Java"
    "walkin interview" "Bengaluru" "Java"
    "walk-in recruitment" "Bengaluru" "Java"
    "Java developer" "walk-in" "Bengaluru"
    "Java backend" "walk-in" "Bengaluru"

## Tasks

- Implement QueryGenerator
- Add technology aliases
- Add role aliases
- Add city normalization
- Add walk-in terminology
- Remove duplicate queries
- Keep query generation independent from provider implementation

## Completion Criteria

Given the same SearchContext, the system can generate a useful set of discovery queries.

---

# 7. Phase 3 — Search Provider Integration

## Goal

Discover candidate URLs from the public web.

## Tasks

- Select the initial search provider
- Create provider adapter
- Configure credentials securely
- Execute generated queries
- Extract result URLs
- Store discovery metadata
- Handle provider errors
- Handle rate limits

## Important Design

Use an abstraction such as:

    JobSource

The discovery engine should not depend directly on provider-specific response objects.

## Completion Criteria

Input:

    Bengaluru + Java

Output:

    List of candidate URLs

At this stage, job extraction is not required.

---

# 8. Phase 4 — URL Processing

## Goal

Prepare discovered URLs before fetching.

## Tasks

- Normalize URLs
- Remove safe tracking parameters where appropriate
- Detect exact duplicates
- Store source information
- Track discovery query
- Track discovery timestamp

## Completion Criteria

The same URL discovered through multiple queries should be processed only once.

---

# 9. Phase 5 — Page Fetching

## Goal

Fetch publicly accessible source pages.

## Tasks

Implement:

- HTTP fetching
- Timeout
- Redirect handling
- Response validation
- Retry/backoff
- Content type handling
- Fetch status
- Failure logging

## Important Rule

Only appropriately accessible public pages should be processed.

The system must not bypass:

- CAPTCHA
- Authentication
- Login requirements
- Technical access controls
- Other restrictions intended to prevent automated access

Applicable crawling restrictions and source terms should be respected.

## Completion Criteria

Input:

    URL

Output:

    RawDocument

or:

    Fetch failure

One failed page must not stop the complete discovery task.

---

# 10. Phase 6 — Raw Document and Text Processing

## Goal

Convert fetched pages into processable documents.

## Tasks

Store:

- Source URL
- Source name
- Raw content
- Content type
- HTTP status
- Content hash
- Discovered timestamp
- Fetched timestamp

Then implement:

    Raw HTML
        ↓
    HTML Cleaning
        ↓
    Clean Text

Remove:

- Scripts
- Styles
- Unnecessary page elements

Preserve useful job-related information.

## Completion Criteria

A fetched page can be converted into clean text suitable for extraction.

---

# 11. Phase 7 — Structured Data Extraction

## Goal

Use structured information when available.

Inspect:

- JSON-LD
- JobPosting structured data
- OpenGraph metadata
- Other useful metadata

Structured data may provide information such as:

- Job title
- Hiring organization
- Location
- Description
- Date posted
- Application information

Structured data is an extraction signal.

It is not automatically proof that the information is correct or current.

## Completion Criteria

The system can extract useful structured information when a page provides it.

---

# 12. Phase 8 — Walk-in Detection

## Goal

Identify whether a page represents a real walk-in opportunity.

Possible signals:

- Walk-in interview
- Walk-in drive
- Walk-in recruitment
- Walk-in hiring
- Walkin
- Interview date
- Interview time
- Interview venue
- Recruitment drive

Classification:

    WALK_IN
    NOT_WALK_IN
    UNCERTAIN

The detector should combine multiple signals.

The presence of the word "walk-in" alone should not automatically classify a page as a valid walk-in opportunity.

## Completion Criteria

The system can separate likely walk-in pages from unrelated job pages.

---

# 13. Phase 9 — Job Information Extraction

## Goal

Convert a walk-in page into a structured JobPosting.

Target fields:

- Company
- Job title
- Description
- City
- Country
- Opportunity type
- Event date
- Event start time
- Event end time
- Venue
- Minimum experience
- Maximum experience
- Skills
- Application information
- Source URL
- Source name

## Extraction Priority

Use the simplest reliable method first:

    Structured Data
         ↓
    Source-specific Parser
         ↓
    DOM Extraction
         ↓
    Text Patterns
         ↓
    AI-assisted Extraction

AI is optional in V1.

It should be introduced only where deterministic extraction is insufficient.

## Completion Criteria

A valid walk-in page can produce a structured candidate opportunity.

---

# 14. Phase 10 — Normalization

## Goal

Convert different source formats into a common internal representation.

Examples:

    Bangalore → Bengaluru

    3-5 years → min=3, max=5

    3+ years → min=3

Technology aliases such as:

    Core Java
    Java Developer
    Java Backend
    Java Engineer

can be normalized for matching.

The original source information should not be unnecessarily lost.

## Completion Criteria

Equivalent information from different sources is represented consistently.

---

# 15. Phase 11 — Validation

## Goal

Reject incorrect or incomplete opportunities before they reach users.

Validate:

- Company
- Job title
- Source URL
- Walk-in evidence
- Location
- Event date when available
- Experience
- Extracted data format
- Expiration

The system should not guess missing information.

## Completion Criteria

Clearly invalid opportunities are rejected or marked appropriately.

---

# 16. Phase 12 — Deduplication

## Goal

Represent one real-world opportunity as one logical opportunity.

Example:

    Company A
    Java Developer
    Bengaluru
    15 September

may appear on:

    Company Website
    Job Board A
    Job Board B
    Aggregator

These should normally be represented as one opportunity with multiple sources.

## Initial Matching Signals

- Company
- Normalized job title
- City
- Event date
- Venue
- Application URL

More advanced similarity can be introduced later.

## Completion Criteria

Duplicate opportunities are merged or linked instead of being shown repeatedly.

---

# 17. Phase 13 — Source Management

## Goal

Maintain complete source traceability.

Track:

- Source name
- Source type
- Source URL
- First discovered
- Last checked
- Source quality information

Possible source types:

    SEARCH_PROVIDER
    COMPANY
    ATS
    JOB_BOARD
    AGGREGATOR
    API
    RSS
    WEB_PAGE

## Completion Criteria

Every opportunity can be traced back to its original source.

---

# 18. Phase 14 — Freshness

## Goal

Prevent outdated walk-in opportunities from appearing as active results.

Track:

- firstSeenAt
- discoveredAt
- lastCheckedAt
- eventDate
- status

Initial statuses:

    ACTIVE
    AGING
    EXPIRED

Basic rule:

    If eventDate is before the current date,
    mark the opportunity as EXPIRED.

Future states may include:

    CANCELLED
    RESCHEDULED

## Completion Criteria

Expired opportunities do not appear as upcoming active opportunities.

---

# 19. Phase 15 — PostgreSQL Persistence

## Goal

Persist normalized opportunities and discovery information.

Initial tables:

    companies
    job_postings
    job_sources
    job_raw_documents
    job_discovery_tasks
    job_skills
    job_posting_skills

The database should support the relationship:

    Opportunity
        ├── Source A
        ├── Source B
        └── Source C

One logical opportunity can have multiple sources.

---

# 20. Phase 16 — Discovery Tasks

## Goal

Represent and track a complete discovery operation.

A DiscoveryTask should track:

- Search criteria
- Status
- Start time
- End time
- URLs discovered
- Pages fetched
- Fetch failures
- Walk-in candidates
- Opportunities extracted
- Opportunities rejected
- Duplicates
- Errors

Initial lifecycle:

    CREATED
       ↓
    PROCESSING
       ↓
    COMPLETED

Failure:

    FAILED

---

# 21. Phase 17 — Asynchronous Discovery

## Goal

Do not make the user wait for the complete discovery pipeline inside a single HTTP request.

Flow:

    API
      ↓
    Create DiscoveryTask
      ↓
    Async Worker
      ↓
    Discovery Pipeline
      ↓
    PostgreSQL

For V1, use a controlled Spring asynchronous mechanism and thread pool.

Kafka or another distributed queue is not required at this stage.

## Completion Criteria

The API can create a discovery task without blocking until all external pages have been processed.

---

# 22. Phase 18 — Search and Ranking API

## Goal

Expose useful stored opportunities through backend APIs.

Example:

    POST /api/v1/discovery/search

Request:

    {
      "city": "Bengaluru",
      "keyword": "Java",
      "experienceMin": 3,
      "experienceMax": 5,
      "type": "WALK_IN"
    }

Response:

    {
      "searchId": "abc123",
      "status": "PROCESSING"
    }

Future result endpoint:

    GET /api/v1/discovery/search/{searchId}

## Ranking Signals

Initial ranking can use:

1. Technology match
2. Role match
3. City match
4. Experience match
5. Event date relevance
6. Freshness
7. Source quality
8. Information completeness

# 23. Phase 19 — Backend End-to-End Validation

## Goal

Prove that the complete backend pipeline works with real data.

Example searches:

    Bengaluru + Java
    Hyderabad + Java
    Gurgaon + Java
    Pune + Software Developer
    Noida + Backend Developer

Measure:

- URLs discovered
- Pages successfully fetched
- Walk-in candidates
- Valid opportunities
- Duplicate count
- Expired count
- Relevant result count
- Extraction completeness
- Processing time

This is a major milestone.

The backend should be reasonably reliable before frontend implementation begins.

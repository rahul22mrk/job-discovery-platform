# V1 Requirements

## 1. V1 Goal

The goal of V1 is to automatically discover relevant walk-in job opportunities from publicly available sources on the internet.

A user should be able to search for walk-in opportunities using simple filters such as:

- City
- Technology / Role
- Experience
- Date range

The system should find relevant public pages, extract job information, remove duplicates, check freshness, and return useful opportunities with their original source links.

The main goal is not to collect the maximum number of jobs.

The goal is to provide relevant, fresh, and trustworthy opportunities.

---

## 2. V1 Scope

V1 will focus only on:

- Walk-in interviews
- Walk-in drives
- Walk-in recruitment events
- Publicly available job/event pages
- Automatic discovery from the public internet
- Basic job information extraction
- Data normalization
- Validation
- Duplicate detection
- Freshness tracking
- Source transparency
- Search and filtering

V1 will use `WALK_IN` as the only supported opportunity type.

The data model should still be designed so that other opportunity types can be added later.

---

## 3. User Search

The user should be able to search using:

### Required

- City
- Technology / Role

### Optional

- Minimum experience
- Maximum experience
- From date
- To date

Example request:

    {
      "city": "Bengaluru",
      "keyword": "Java",
      "experienceMin": 3,
      "experienceMax": 5,
      "fromDate": "2026-09-01",
      "toDate": "2026-09-30",
      "type": "WALK_IN"
    }

The UI should remain simple.

Users should not need to understand how the discovery system works internally.

---

## 4. Discovery Requirements

When a search is submitted, the backend should create a discovery task.

The discovery process should:

1. Accept the user's search criteria.
2. Generate relevant search queries.
3. Search supported public sources.
4. Collect relevant URLs.
5. Fetch publicly accessible pages.
6. Extract page content.
7. Detect whether the page contains a walk-in opportunity.
8. Extract structured job information.
9. Normalize the extracted information.
10. Validate important fields.
11. Detect duplicate opportunities.
12. Check freshness.
13. Store valid opportunities.
14. Return relevant results to the user.

The discovery process should not require the user to manually provide URLs.

---

## 5. Search Query Generation

The system should generate multiple query variations from the user's search criteria.

For example:

City: Bengaluru  
Technology: Java

Possible queries:

    "walk-in interview" "Bengaluru" "Java"
    "walk-in drive" "Bengaluru" "Java"
    "walkin interview" "Bengaluru" "Java"
    "walk-in recruitment" "Bengaluru" "Java"
    "Java developer" "walk-in" "Bengaluru"
    "Java backend" "walk-in" "Bengaluru"

The query generation logic should be implemented separately from the rest of the discovery flow.

This will allow new query strategies to be added later.

---

## 6. Source Discovery

The system should support an abstraction for discovering public pages.

Example:

    public interface JobSource {

        List<DiscoveredPage> discover(SearchContext context);

    }

V1 may start with a limited number of source implementations.

The architecture should allow additional sources to be added later without changing the core discovery flow.

Possible future sources:

- Search engines
- Company career pages
- Job boards
- Job aggregators
- RSS feeds
- Public APIs

Only publicly accessible and permitted sources should be used.

The system must not bypass:

- Login requirements
- CAPTCHA
- Access restrictions
- Robots/access policies
- Other technical restrictions intended to prevent automated access

---

## 7. Page Fetching

For discovered URLs, the system should fetch publicly accessible page content.

The fetcher should:

- Handle HTTP errors
- Handle redirects
- Respect reasonable timeouts
- Avoid repeatedly fetching the same URL unnecessarily
- Record when a page was checked
- Fail gracefully when a page cannot be accessed

A failed page fetch should not stop the complete discovery task.

---

## 8. Walk-in Detection

The system should determine whether a page actually represents a walk-in opportunity.

Strong signals may include:

- Walk-in interview
- Walk-in drive
- Walk-in recruitment
- Walk-in hiring
- Walkin
- Interview date
- Interview time
- Interview venue

The detector should avoid treating every job mentioning the word "walk-in" as a valid walk-in opportunity.

The system should prefer opportunities with actual event information.

If there is not enough evidence that a page represents a walk-in opportunity, it should not be shown as a V1 result.

---

## 9. Information Extraction

The system should extract useful information from a discovered page.

Target fields include:

- Company
- Job title
- Description
- City
- Country
- Opportunity type
- Event date
- Event start time
- Event end time
- Venue
- Experience minimum
- Experience maximum
- Skills
- Application information
- Source name
- Source URL
- Discovery time
- Last checked time
- Status

Example:

    {
      "company": "Example Company",
      "title": "Java Backend Developer",
      "city": "Bengaluru",
      "type": "WALK_IN",
      "eventDate": "2026-09-20",
      "venue": "Example Business Park",
      "experienceMin": 3,
      "experienceMax": 5,
      "skills": [
        "Java",
        "Spring Boot",
        "Microservices"
      ],
      "sourceUrl": "https://example.com/job",
      "status": "ACTIVE"
    }

The system must not guess important information.

If a field cannot be reliably extracted, it should remain empty.

---

## 10. Data Normalization

Different websites may describe the same information differently.

The system should normalize common variations.

Examples:

- Bangalore → Bengaluru
- 3-5 years → experienceMin=3, experienceMax=5
- 3+ years → experienceMin=3

Technology aliases should also be normalized.

Example:

- Java
- Java Developer
- Core Java
- Java Backend
- Java Engineer

may all be associated with the Java technology category internally.

Normalization should improve matching without changing the original source information.

---

## 11. Validation

Before storing an opportunity, the system should validate the extracted data.

Important validation checks include:

- Source URL exists
- Company can be identified
- Job title can be identified
- Opportunity is actually a walk-in
- Event date is valid when available
- City is relevant
- Extracted information is not obviously corrupted
- Source page is publicly accessible
- Opportunity is not expired

An opportunity that fails important validation should not be shown as a normal result.

---

## 12. Duplicate Detection

The same walk-in opportunity may appear on multiple websites.

The system should detect duplicates and store a single logical opportunity whenever possible.

Potential duplicate signals:

- Same company
- Same job title
- Same city
- Same event date
- Same venue
- Similar description
- Same application link
- Similar source content

Example:

Company A - Java Developer Walk-in - Bengaluru - 20 Sep

found on three different websites should ideally appear as one opportunity.

The system may store multiple source references for the same opportunity.

Example:

Found on 3 sources

This can also become a trust signal.

---

## 13. Freshness

Walk-in opportunities are time-sensitive.

The system should track:

- discoveredAt
- lastCheckedAt
- eventDate
- status

A basic status model:

- ACTIVE
- AGING
- EXPIRED

An opportunity should automatically become `EXPIRED` after the relevant event date has passed.

The system should also be able to detect when the original page is no longer available.

Freshness should be considered when ranking search results.

---

## 14. Source Transparency

Every opportunity should show where the information came from.

A user should be able to:

- See the source name
- Open the original source page
- Understand when the page was last checked

The platform should not hide the original source.

The first version should prioritize transparency over making the platform appear to be the original publisher of the job.

---

## 15. Trust Signals

V1 should provide simple trust signals based on available evidence.

Possible signals include:

- Source available
- Event date found
- Venue found
- Application link found
- Recently checked
- Multiple sources found
- Company source available

The system should not claim that a job is "verified" unless there is an actual verification process supporting that claim.

Internally, extraction confidence and verification status should remain separate concepts.

---

## 16. Search Results

Search results should be ranked based on relevance.

Initial ranking factors:

1. Technology match
2. Role match
3. City match
4. Experience match
5. Event date relevance
6. Freshness
7. Source quality
8. Information completeness

The ranking system should favor useful opportunities instead of simply sorting by discovery time.

---

## 17. API

V1 should expose an API for discovery.

Example endpoint:

    POST /api/v1/discovery/search

Request:

    {
      "city": "Bengaluru",
      "keyword": "Java",
      "experienceMin": 3,
      "experienceMax": 5,
      "fromDate": "2026-09-01",
      "toDate": "2026-09-30",
      "type": "WALK_IN"
    }

Initial response:

    {
      "searchId": "abc123",
      "status": "PROCESSING"
    }

Discovery should run asynchronously.

The user should not have to keep an HTTP request open while the system searches multiple sources.

---

## 18. Discovery Task

Each search should create a discovery task.

A task should have a lifecycle similar to:

    CREATED
       ↓
    PROCESSING
       ↓
    COMPLETED

Failure state:

    FAILED

The system should record enough information to understand what happened during a discovery task.

Examples:

- Search criteria
- Start time
- End time
- Number of URLs discovered
- Number of pages fetched
- Number of walk-ins detected
- Number of valid opportunities
- Number of duplicates
- Error count

Detailed observability can be improved later.

---

## 19. Asynchronous Processing

Discovery should be asynchronous.

For the first implementation, a simple Spring-based asynchronous mechanism is sufficient.

Example architecture:

    User
      ↓
    Discovery API
      ↓
    Create Discovery Task
      ↓
    Async Discovery Worker
      ↓
    Query Generation
      ↓
    Source Discovery
      ↓
    Fetch
      ↓
    Extract
      ↓
    Validate
      ↓
    Deduplicate
      ↓
    Store

A message broker such as Kafka is not required for V1.

The architecture should allow asynchronous processing to evolve later.

---

## 20. Database

PostgreSQL will be used as the initial database.

V1 should primarily require data for:

- companies
- job_postings
- job_sources
- job_raw_documents
- job_discovery_tasks
- job_skills
- job_posting_skills

The schema should avoid unnecessary complexity.

Future tables such as:

- users
- saved_searches
- notifications

will be added when those features are actually implemented.

---

## 21. Backend Architecture

The backend should start as a modular monolith.

Initial logical modules:

- discovery
- extraction
- normalization
- validation
- deduplication
- ranking
- search
- common

These are logical boundaries, not separate services.

The project should not be split into microservices during V1 unless there is a real need.

---

## 22. Generic Opportunity Model

The core model should not be hardcoded only for walk-ins.

Example:

    public enum JobOpportunityType {

        WALK_IN,
        JOB,
        HIRING_DRIVE
    }

V1 will only use:

    WALK_IN

Future opportunity types can be added without redesigning the complete system.

---

## 23. Out of Scope for V1

The following features are intentionally excluded from V1:

- User registration
- User profiles
- Resume upload
- Resume parsing
- Resume matching
- Saved searches
- Email notifications
- WhatsApp notifications
- Push notifications
- Job applications inside the platform
- Company accounts
- Recruiter accounts
- Recruiter dashboard
- Payments
- Premium subscriptions
- AI resume generation
- AI interview preparation
- Automatic application
- Full job portal functionality
- LinkedIn automation
- Naukri automation
- CAPTCHA bypass
- Login-protected scraping
- Complex recommendation systems
- Kafka
- Kubernetes
- Microservices
- Advanced distributed infrastructure

These may be considered after the core discovery system proves useful.

---

## 24. Non-Functional Requirements

### Reliability

One source failing should not stop the complete discovery process.

### Performance

The API should return quickly after creating the discovery task.

The heavy discovery work should happen asynchronously.

### Scalability

The source, extraction, normalization, and validation components should be replaceable and extensible.

### Maintainability

Core responsibilities should remain separated.

For example:

    Discovery ≠ Extraction
    Extraction ≠ Validation
    Validation ≠ Deduplication
    Deduplication ≠ Ranking

### Observability

The system should provide enough logs to understand:

- What search was executed
- Which sources were queried
- Which URLs were found
- Which pages failed
- Which opportunities were extracted
- Which opportunities were rejected
- Which duplicates were detected

### Data Quality

Incorrect or incomplete data should not be silently presented as fact.

---

## 25. Acceptance Criteria

V1 will be considered successful when the system can:

- Accept a city and technology/role search.
- Generate multiple relevant search queries.
- Discover publicly accessible pages.
- Fetch discovered pages.
- Detect walk-in opportunities.
- Extract structured job information.
- Normalize common data variations.
- Validate extracted opportunities.
- Remove or merge duplicates.
- Track freshness.
- Store valid opportunities in PostgreSQL.
- Return relevant opportunities to the user.
- Provide the original source URL for each opportunity.
- Handle source/page failures without crashing the complete discovery process.
- Run discovery asynchronously.

---

## 26. V1 Success Metrics

The first version should be evaluated primarily on data quality.

Important metrics:

### Relevance

How many returned opportunities actually match the user's search?

### Freshness

How many returned opportunities are still valid?

### Duplicate Rate

How often is the same opportunity shown multiple times?

### Completeness

How often do opportunities contain useful information such as:

- Company
- Role
- Date
- Venue
- Experience
- Source

### Source Coverage

How many useful public sources can the system discover?

### Discovery Success

For a given search, how often does the system find at least one relevant opportunity?

The initial goal is not maximum traffic or maximum number of listings.

The initial goal is a reliable discovery engine.

---

## 27. V1 Product Principle

The product should follow this principle:

    Search
       ↓
    Discover
       ↓
    Extract
       ↓
    Validate
       ↓
    Deduplicate
       ↓
    Rank
       ↓
    Show useful opportunities
       ↓
    Let the user verify through the original source

The platform should optimize for:

    Relevance > Quantity
    Freshness > Volume
    Trust > Hype
    Simplicity > Complexity

V1 should solve one problem well:

> "I want to find relevant upcoming walk-in opportunities without manually searching the internet across many websites."

Once this works reliably, the same discovery engine can be expanded to regular jobs, company-specific opportunities, hiring drives, and other job-discovery use cases.
